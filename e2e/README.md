# Playwright E2E

Написаны 18 браузерных сценариев для роли тренера, подтверждения email и рейтинга.
Зависимости клиента и E2E установлены через pnpm 12.18.0, Chromium для Playwright
загружен. Версии закреплены в `pnpm-lock.yaml`. Проверки типов клиента и E2E прошли.
Итоговый полный прогон 6 ноября 2026 года: **18 из 18 сценариев прошли**.
Сохранены 33 видео для 18 сценариев в
`e2e/artifacts/2026-11-06T13-34-20-147Z/`.

## Что проверяется

`specs/coach.spec.ts`:

- Создание ученика через форму тренера, привязка к тренеру, сохранение его сессии.
- Вход ученика с паролем сразу после создания, без подтверждения почты.
- Заявка на соревнование: комментарий и запись об оплате появляются, допуска ещё нет.
- Подтверждение главным судьёй добавляет участника ровно один раз; статус сохраняется после перезагрузки.
- Отклонение и повторные запросы: третью заявку можно принять или отклонить;
  после третьего отказа четвёртая отправка недоступна и тренеру, и самому ученику.
- Поиск любого участника, включая аккаунты другого тренера и независимого участника, без отображения email; закрытые страницы главного судьи и тренера для других ролей.
- Повторяющийся email не перезаписывает чужой аккаунт.
- Закрытая регистрация, начатый или завершённый турнир, несовпадение требований.
- Обычный участник по-прежнему отправляет заявку через свой экран оплаты и получает допуск от судьи.

`specs/email-confirmation.spec.ts`:

- Регистрация на десктопе → настоящее SMTP-письмо → ссылка на телефоне → вход на обоих устройствах.
- Ссылка сама не создаёт сессию; email на странице входа подставляется правильно, включая `+` в адресе.
- До подтверждения вход запрещён; подтверждение в исходном браузере также работает.
- Перезагрузка и повторное открытие ссылки безопасны.
- Уже открытая сессия другого пользователя на телефоне сохраняется.
- Отсутствующий код, неверный код и неизвестный email не подтверждают аккаунт;
  исходная корректная ссылка после этого остаётся рабочей.
- Одновременное открытие ссылки в двух независимых браузерных контекстах.

`specs/rating.spec.ts`:

- Аккаунт без подтверждённого email отсутствует на странице рейтинга и в ответе API, включая общее число записей.

Все действия проверяемых сценариев идут через настоящий интерфейс React и Express API.
Нет подмен HTTP, Mongoose, Redux или почтового транспорта. MongoDB используется
для подготовки данных, дополнительных проверок результата и удаления своих записей.
Ссылки подтверждения берутся из писем Mailpit, а не из поля `oneTimeCode` базы.
«Телефон» — отдельный контекст Chromium с мобильной эмуляцией; это не реальное устройство и не проверка Safari.

## Данные и изоляция

Перед **каждым** тестом fixture создаёт тренера, второго тренера, главного судью,
по одному ученику каждого тренера, самостоятельного участника и открытый турнир.
Роль тренера назначается непосредственно при подготовке аккаунта в MongoDB,
что соответствует ручному назначению роли в приложении. Даты турнира рассчитываются
от текущего времени. Создание турнира — подготовка через БД: отдельной пользовательской
формы создания соревнования в этих сценариях нет.

Каждый тест и каждый повтор получает UUID в адресах и названиях. Тесты выбирают
конкретный турнир по ID, поэтому подходят как для пустой базы, так и для существующей
тестовой базы с другими пользователями и турнирами. Существующие записи не обновляются.

В `finally` удаляются только турниры с сохранёнными ID и пользователи с точными
адресами, зарезервированными этим тестом. Адрес резервируется **до** создания
аккаунта через UI, чтобы убрать его и при падении сценария. Сначала закрываются
браузерные контексты. Чужие записи и коллекции не удаляются, индексы не пересоздаются.
При принудительном завершении процесса очистка может не выполниться;
UUID для поиска оставшихся записей прикладывается к отчёту как `fixture-namespace`.

Прочитанные письма подтверждения удаляются по точным ID. Остальные письма,
включая уведомления судье, остаются в локальном Mailpit до перезапуска контейнера.
SMTP relay не настроен, поэтому реальные адресаты уведомлений их не получают.

## Подготовка и запуск позже

Установка зависимостей и Chromium уже выполнена. Чтобы повторить только первый сценарий:

```powershell
pnpm --dir e2e exec playwright test specs/email-confirmation.spec.ts --grep "desktop signup, email link on a phone, password login on both devices" --workers=1 --retries=0
```

Команды полного запуска ниже предназначены для следующего этапа.
Нужны зависимости самого клиента и сервера, Node.js 22+ и Docker Compose.
E2E — отдельный пакет со своим pnpm-lock.yaml и зависимостями.

Из корня репозитория:

```powershell
pnpm --dir e2e install --frozen-lockfile
pnpm --dir e2e exec playwright install chromium
docker compose -f e2e/compose.yaml up -d
pnpm --dir e2e test
```

Playwright сам запускает сервер на `3001` и Vite на `5173`. Эти порты должны
быть свободны: уже работающий dev-сервер намеренно не переиспользуется, чтобы API
и подготовка данных гарантированно использовали одну базу. MongoDB слушает `27018`,
SMTP — `1025`, интерфейс и API Mailpit — `8025`. Все порты Docker доступны только локально.

По умолчанию используется `mongodb://127.0.0.1:27018/chessbox_e2e`.
Можно выбрать уже существующую **тестовую** базу:

```powershell
$env:E2E_MONGO_URI = 'mongodb://127.0.0.1:27018/existing_test_database'
pnpm --dir e2e test
```

Конфигурация передаёт один и тот же URI серверу и fixtures; `server/.env.test`
не читается раннером. JWT и SMTP задаются локальными E2E-значениями. Других ручных
настроек `.env` для стандартного запуска не требуется.

```powershell
pnpm --dir e2e test:ui
pnpm --dir e2e test --grep "desktop signup"
pnpm --dir e2e typecheck
pnpm --dir e2e report
docker compose -f e2e/compose.yaml stop
```

Каждый запуск сохраняется в отдельный каталог `e2e/artifacts/<UTC-время>/`:
HTML-отчёт в `report/index.html`, результаты и видео в `results/`.
Видео каждого браузерного контекста сохраняется **всегда**, включая успешные тесты,
и прикладывается к HTML-отчёту. В первом сценарии `actor-0-page-0.webm` — десктоп,
`actor-1-page-0.webm` — телефон. Новые запуски не удаляют предыдущие записи.
При ошибке сохраняются общий trace Playwright и screenshots участников сценария.
Файлы результатов и отчётов исключены из Git. Для воспроизводимости используется
`e2e/pnpm-lock.yaml`.

## Минимальная поддержка в приложении

- `server/constants.ts`: явный `SMTP_HOST` включает обычный SMTP-транспорт;
  без него сохраняется существующая настройка Gmail. E2E направляет письма в Mailpit.
- `tableSchemaPaymentCheck.tsx`: `data-testid="payment-review"` позволяет найти
  строку конкретного участника без привязки к CSS и структуре вложенных `div`.

Fixtures организованы по [документации Playwright](https://playwright.dev/docs/test-fixtures),
чтение писем — через [Mailpit API v1](https://mailpit.axllent.org/docs/api-v1/).
